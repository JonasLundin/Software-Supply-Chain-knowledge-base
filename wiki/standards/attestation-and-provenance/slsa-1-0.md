# Summary

**SLSA v1.0 (Supply-chain Levels for Software Artifacts)** is a comprehensive security framework developed by the Open Source Security Foundation (OpenSSF) to safeguard software artifacts from tampering, unauthorized modifications, and supply chain attacks[^slsa-framework]. Originating from Google's internal Binary Authorization for Borg (BAB) practices, SLSA provides a standardized, incremental checklist of security controls that give consumers confidence in the integrity and origin of software artifacts.

SLSA v1.0 established a modular "tracks" architecture, formally decoupling the **Build Track** from other supply chain aspects (Source, Dependencies) to accelerate adoption and provide immediate, unforgeable verification of the build process.

# Technical Scope / Normative Requirements

### The SLSA v1.0 Build Track

SLSA v1.0 structures build security into three ascending, measurable levels:

| Level | Core Requirement | Verification & Security Guarantee |
| :--- | :--- | :--- |
| **Build L1** | **Provenance Exists** | The producer generates machine-readable provenance recording how the artifact was built, the top-level source repository, and entry-point arguments. Provenance may be self-generated on developer workstations; it does not guarantee tamper-resistance. |
| **Build L2** | **Hosted Build Platform** | The build executes on a hosted service (e.g. GitHub Actions, GitLab CI, Google Cloud Build). The provenance is cryptographically generated and signed by the build service itself rather than tenant code, preventing the build script from forging its own origin metadata. |
| **Build L3** | **Hardened Build Platform** | The build platform guarantees strong isolation between builds. Each build runs in an ephemeral, freshly provisioned environment. Tenant code cannot modify external parameters or cache layers to compromise subsequent builds. |

# Applicability & Operational Impact

- **Software Producers**: Enables organizations to demonstrate adherence to secure software development standards (such as NIST SP 800-218 task PS.2) by producing cryptographically unforgeable proof of compilation.
- **Build Platforms**: Guides infrastructure hardening for CI/CD providers (e.g. ephemeral container runners, OIDC-based identity delegation, isolation boundaries).
- **Software Consumers**: Allows deployment policy engines (e.g. Kubernetes admission controllers) to verify that binaries running in production originated from authorized GitHub workflows rather than unauthorized developer laptops.

# Practical Implementation

### Generating SLSA Provenance in GitHub Actions

The OpenSSF provides official reusable workflows (`slsa-github-generator`) that achieve **SLSA Build L3**:

```yaml
name: SLSA Build L3 Release
on:
  push:
    tags:
      - 'v*'

jobs:
  build:
    outputs:
      hashes: ${{ steps.hash.outputs.hashes }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build Binary
        run: |
          go build -o myapp-linux-amd64 .
      - name: Generate Subject Hashes
        id: hash
        run: |
          sha256sum myapp-linux-amd64 | base64 -w0 > hashes.txt
          echo "hashes=$(cat hashes.txt)" >> "$GITHUB_OUTPUT"

  provenance:
    needs: [build]
    permissions:
      actions: read
      id-token: write
      contents: write
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@v2.0.0
    with:
      base64-subjects: "${{ needs.build.outputs.hashes }}"
      upload-assets: true
```

### Verifying Provenance with slsa-verifier

Consumers verify the binary against the signed SLSA attestation:

```bash
# Verify artifact matches provenance and source repository
slsa-verifier verify-artifact myapp-linux-amd64 \
  --provenance-path myapp-linux-amd64.intoto.jsonl \
  --source-uri github.com/acme/auth-service \
  --source-tag v2.4.0
```
